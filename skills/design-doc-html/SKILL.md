# design-doc-html

Markdownの設計書・要件定義書を、単一HTMLの設計書に変換する。

## このスキルの立ち位置

**変換ツールである。分析ツールではない。**

入力に書かれていないことを補って書かない。新しい設計判断をしない。やるのは次の3つだけ。

1. **並べ替え** — 実装者の組み立て順で書かれた文書を、読み手が理解する順に組み替える
2. **要約** — 冗長な記述を圧縮する。ただし判断の根拠になる具体値（時刻、閾値、式、条件）は削らない
3. **抽出** — 本文に散らばった「なぜそう決めたか」を1箇所に集める

この3つを超えたら、それは <span>導出</span> か <span>記載なし</span> として明示する。黙って補完してはいけない。

## 手順

### 1. 入力を読む

対象のMarkdownを全部読む。長くても飛ばさない。

### 2. 記述を4つに分類する

読みながら、各段落・各表を次のどれかに割り振る。この分類が変換の中身になる。

| 分類 | 例 | 行き先 |
|---|---|---|
| 意図・判断 | なぜこの方式を選んだか、何を守るための制約か | 設計判断と理由 |
| 構造の合意 | データモデル、API、ファイル構成、依存関係 | 構成一覧・コードグラフ |
| 振る舞い | 画面の挙動、時刻ルール、状態の変化 | 仕様概要・詳細 |
| 実装手順 | 具体的なコード、ライブラリのバージョン、DI登録の順序 | 詳細（折りたたみ）または省略 |

**「意図・判断」は本文の中に埋もれている。** 仕様の説明文に「〜のため」「〜だと〜になってしまうため」という形で紛れているので、拾って設計判断の表に移す。これがこのスキルの一番の仕事。

### 3. 欠落を記録する

各セクションについて、入力に記述があるか確認する。無いものは推測で埋めず、次のように扱う。

- 本文には `<span class="missing">記載なし</span>` を出す
- 「まだ決まってないこと」の表に、項目・状況・効いてくるところを書く

特に **背景／解決／ユースケース／設計判断の理由** は欠けていることが多い。欠けていること自体が設計書の価値ある情報なので、必ず可視化する。

### 4. テンプレートに流し込む

`template.html` をコピーし、プレースホルダを置換する。

| プレースホルダ | 中身 |
|---|---|
| `{{TITLE}}` | 「〇〇 設計書」 |
| `{{SOURCE_FILE}}` | 入力ファイル名 |
| `{{DATE}}` | 変換日（YYYY-MM-DD） |
| `{{TOC}}` | 目次の `<a>` 群 |
| `{{BODY}}` | 本文 |

**CSSとJavaScriptは書き換えない。** テンプレートに含まれるCDN構成・フォールバック処理・配色は完成しているので、そのまま使う。

### 5. 検証する

出力後、次を確認する。

- 入力に無い固有名詞・数値・条件が出力に混ざっていないか
- 「まだ決まってないこと」に、本文の `記載なし` がすべて対応しているか
- 折りたたみを全部閉じた状態で、上から順に読めるか

## セクション構成

この順序で出す。入力側の章立ては使わない。**セクションを増やさない。**

| # | セクション | 内容 |
|---|---|---|
| 01 | 仕様概要 | これが何をするものかの箇条書き。5〜7項目、1項目1行 |
| 02 | 背景と解決 | 2枠並び。なぜ必要になったか／それが何を解決するか |
| 03 | 対象外 | この設計書が扱わないこと。箇条書き |
| 04 | ユースケース | 前提／もし／ならば の3行カード。3〜6件 |
| 05 | 設計判断と理由 | 「決めたこと」と「理由」の2列表 |
| 06 | 構成一覧 | リポジトリ構成（ツリー）、ファイル概要（表）、API一覧（表） |
| 07 | コードグラフ | mermaidの依存関係図。必要なら状態遷移図も |
| 08 | 詳細 | ファイル単位の折りたたみ。要件の箇条書き＋想定コード |
| 09 | まだ決まってないこと | 項目／状況／効いてくるところ の3列表 |

改修案件（既存コードへの変更）の場合は、06 に区分列（新規／更新／削除）を足し、07 のノードを区分で色分けする。新規プロダクトの場合は区分が付かないので、その旨を注記する。

## 分量の制約

制約を数値で守らないと、入力と同じだけ長い文書になる。

- 仕様概要：**7項目以内**、1項目1行
- 各箇条書き：**1項目60字以内**
- ユースケース：**6件以内**
- 折りたたみを閉じた状態で **スクロール4画面以内**
- 詳細に書くのは次のどれかに当てはまるファイルだけ。**それ以外は構成一覧の1行で済ませる**
  - 非自明な判断が入っている
  - 他所への影響がある
  - 落ちたときの挙動を決めている

## バッジの使い分け

| 記法 | 使うとき |
|---|---|
| `<span class="missing">記載なし</span>` | 入力にその情報が無い |
| `<span class="derived">導出</span>` | 入力の記述から起こしたもの（図、ユースケース、想定コードのシグネチャ） |

**導出したものは必ず「まだ決まってないこと」にも載せる。** 読み手が確認すべき対象だから。

出典（§番号）は付けない。ヘッダのファイル名だけで足りる。

## mermaidの書き方

### コードグラフ

```
flowchart LR
  subgraph B["ブラウザ"]
    direction TB
    A["main.js<br/>初期化・週の状態管理"]
  end
  subgraph S["サーバー"]
    direction TB
    C["Endpoints.cs<br/>ルーティング"]
  end
  A --> |"HTTP /api/tasks"| C
  X -.-> Y
```

- ノードラベルは `<br/>` で「ファイル名」と「役割」の2行にする
- **実線 `-->` は入力に根拠がある呼び出し、点線 `-.->` は役割から推測した呼び出し**
- 図の下に凡例を置き、実線・点線の本数を書く
- 推測が多い場合は、その旨を `<p class="warn">` で注記し、未決事項にも載せる
- `subgraph` で層（ブラウザ／サーバー、フロント／バックなど）を分ける
- ノードが20を超えたら、範囲を絞るか図を分割する

### 状態遷移図

nullableなフィールドや状態を表す列があれば `stateDiagram-v2` で起こす。**図にすると経路の抜けが見つかる**ので、必ず試す。判定できない経路は矢印にラベルで「未定」と書き、未決事項に載せる。

## コードの書き方

想定コードは **シグネチャと制約のコメントだけ**。実装本体は書かない。実装とズレた瞬間に嘘になるため。

入力に実コード（SQLのDDLなど）がある場合はそのまま載せてよい。合意事項そのものなので腐らない。

`<pre><code class="language-xxx">` で言語を指定する。ファイルツリーは `language-plaintext` を指定する（自動検出させると誤った色が付く）。

## やってはいけないこと

- 入力に無い設計判断を書く
- 入力に無い数値・閾値・ライブラリ名を書く
- 「一般的にはこうする」で欠落を埋める
- セクションを増やす、順序を変える
- CSSやJavaScriptを書き換える
- CDNのバージョンを勝手に上げる（テンプレートのバージョンはCDN上での実在を確認済み）

## 出力

`<入力ファイル名>-design.html` として、入力と同じ場所に出力する。
