Gitで「混ざった」「戻したい」を
自力で直せるようになる実践ガイド

別ブランチ用の修正を置いたまま作業して、うっかり今のブランチにコミットしてしまう。そのあと何をすればいいかを、実際の作業の流れに沿って順番に説明します。この資料のコマンドはすべて Git 2.43.0 で実際に実行して動作を確認し、出力も実物を載せています。

この資料の前提：なぜ、こんなことを書いているのか

もともとの作業スタイル 1つのブランチで複数のファイルを編集している途中に、別のブランチで作業する必要が出ることがあります。そのとき、編集中のファイルはコミットせずに放置したまま別のブランチへ移り、そこで作業した分だけをコミットします。元のブランチへ戻ったら、放置していた変更を続きの作業に混ぜる。この資料は、この作業スタイルを前提にしています。

この作業スタイルには、次の3つの困りごとがあります。

  1. 別ブランチ用の変更を、間違って今のブランチにコミットしてしまう。「どのファイルが別用か」をずっと覚えておく必要があり、気を張り続けるのがつらい。
  2. コミットしてしまったあとの直し方が分からない。ファイルだけ外す、直前のコミットに混ぜる、メッセージを直す、Git管理から外す、といった操作のやり方が分からない。
  3. stash を使えば済みそうだが、使い方と「何が入るのか」が分からず、使えていない。stash は何個も作れるので、あとで「どれが何のため」か分からなくなりそうで不安。

この資料は、この3つに答えるために、実際の作業の流れ（別作業が入る → うっかり混ざってコミット → 直す → 失敗したら戻す）の順に書いています。途中で出てくるコマンドは、すべて実際に実行して確認した結果です。

環境ターミナルで Git を使う（GUIツールの操作は扱いません）。Git 2.43.0 で動作確認。ローカルでの作業が中心。

先に結論：3つの困りごとへの答え

1

困りごと1：「未コミットのまま別ブランチへ持ち越す」運用は、動きますが事故りやすいです。

「どれが別ブランチ用か」を頭で覚えておく必要があるのが原因です。別用の変更を stash か WIPコミット で預けるか、git worktree で別フォルダにしてしまうと、覚えておく必要がなくなります。コミットするときは git commit -m "..." -- ファイル名 で名指しすると、置いてあるファイルは混ざりません。→ 第2章・第4章

2

困りごと3：stash で基本的にはOKです。ただし「全部入る」わけではありません。

git stash push -m "メモ" -- ファイル名 で、ファイルを指定して預けられます。新規ファイルは -u も必要です。すでにコミットしたものは stash に入りません。戻すときに、戻す先で同じファイルが変わっていると衝突しますが、stash は残るので失われません。→ 2-3b

3

困りごと2：混ざったファイルは、コミットから外せます。

git reset HEAD~ -- ファイル名 のあと git commit --amend --no-edit。手元のファイルの中身は消えません。→ 3-5

4

直前のコミットに混ぜる・メッセージを直す・Git管理から外す。

混ぜる：git commit --amend --no-edit。メッセージ：git commit --amend --only -m "新"。管理から外す：git rm --cached ファイル名（.gitignore に書くだけでは外れません）。→ 3-4・3-7・3-8

5

worktree は、ブランチを何度も行き来するときや、元の作業に触れたくないときに使います。

ブランチごとに別フォルダで作業でき、切り替えも stash も要りません。ただし、.gitignore 対象のファイルは新しいフォルダに引き継がれません。メリットとデメリットは 2-5 に詳しく書きました。

6

失敗しても、コミットに関する操作は git reflog から戻せます。

ただしコミットしていない変更は戻せません。危ない操作の前には stash か backup ブランチで退避します。→ 第5章

第1章　土台：Gitの「3つの置き場所」と、画面の読み方

1-1　3つの置き場所

これから出てくる操作は、ぜんぶこの図の中の「どこからどこへ動かすか」の話です。先にここだけ押さえてください。

1-2　git status -s の読み方

git status は「いまの状態」を表示するコマンドです。-s は --short の略で、同じ内容を1ファイル1行の短い形式で表示します。まず、同じ状態を2つの形式で見比べます。

git status（長い形式）

ターミナル
On branch mainChanges to be committed:  (use "git restore --staged <file>..." to unstage)	modified:   docs/README.mdChanges not staged for commit:  (use "git add <file>..." to update what will be committed)  (use "git restore <file>..." to discard changes in working directory)	modified:   src/Api/UserController.cs

git status -s（短い形式）

ターミナル
M  docs/README.md M src/Api/UserController.cs

上の長い形式の「Changes to be committed（コミットされる予定）」が 1文字目、「Changes not staged for commit（まだステージしていない）」が 2文字目 に対応します。

行の見方：1文字目と2文字目は、別々の場所の状態

覚えるのはこれだけ

次の git commit に入るのは、「1文字目」に文字があるファイルだけ。1文字目が空白（または ??）のファイルは、コミットに入りません。

色について：資料の色と、ターミナルの色は別物です

この資料では「ステージ＝琥珀色、作業ツリー＝青」と色分けしていますが、実際のターミナルの git status -s は別の色で表示されます（実際に色付きで出力して確認しました）。

場所この資料の色ターミナルの色
1文字目（ステージ）琥珀色緑
2文字目（作業ツリー）青赤
??（未追跡）—赤（2文字とも）
ターミナルの表示イメージ
M  docs/README.md          ← 緑のM＝ステージ済み（次のコミットに入る） M src/Api/UserController.cs  ← 赤のM＝未ステージ（入らない）?? Memo.cs                  ← 赤の??＝未追跡（入らない）

ターミナルでは、緑＝ステージ済み（コミットされる）／赤＝まだ（コミットされない）と覚えると分かりやすいです。「赤＝危険」という意味ではなく、「まだステージしていない」という意味です。

文字の意味

表示（␣は空白1文字）意味次のコミットに入る？
␣M編集したが、ステージしていない入らない
M␣ステージ済み（その後は編集していない）入る
MMステージ済みで、その後さらに編集したステージした版だけ入る
A␣新規ファイルをステージ済み入る
D␣「削除する」をステージ済み削除として入る
␣Dファイルを消したが、ステージしていない入らない
??未追跡（Gitがまだ知らない新規ファイル）入らない
UU衝突している（マージ・stash の戻し中など）直すまでコミット不可

文字は頭文字です。M＝Modified（変更）、A＝Added（追加）、D＝Deleted（削除）、U＝Unmerged（衝突）。

1-3　コマンドの後ろの -s や --stat って何？

-s や --stat のような、コマンドの後ろに付ける指示をオプションと呼びます。出力の形や、コマンドの動き方を変えます。

オプションの書き方

  • 短い形：ハイフン1つ＋1文字（-s、-m）。
  • 長い形：ハイフン2つ＋単語（--short、--message）。
  • 同じ意味の短い形と長い形があることが多く、git status -s と git status --short は同じです。
同じ文字でも、コマンドが違うと意味が違います
コマンド-s の意味
git status -s--short（短い形式で表示）
git show -s（git diff -s なども同じ）--no-patch（差分を表示しない）
git ls-files -s--stage（ステージの情報を表示）

なので「-s はこういう意味」と決め打ちせず、コマンドごとに意味を確認するのが安全です（git コマンド名 --help で確認できます）。

--stat は -s とは別物です

--stat は「どのファイルが何行変わったかの一覧表」を出すオプションです（statistics＝統計の略）。git status -s の -s とは無関係です。同じ状態で実際に出力を比べます。

ターミナル（直前のコミット「second」を調べる）
git show --stat --format='%h %s'dfac41f second Memo.cs        | 1 + docs/README.md | 1 + 2 files changed, 2 insertions(+)# --stat：ファイルごとの変更行数の表git show -s --format='%h %s'dfac41f second# -s（show では --no-patch）：差分を出さず、見出しだけgit show --name-only --format='%h %s'dfac41f secondMemo.csdocs/README.md# --name-only：ファイル名だけgit show --name-status --format='%h %s'dfac41f secondA	Memo.csM	docs/README.md# --name-status：A（追加）/ M（変更）/ D（削除）付きのファイル名

--format='%h %s' は出力の書式の指定で、%h は短縮したコミットID、%s はコミットメッセージの1行目です。この資料では出力を短くするために付けています。

--stat は、git diff --stat（まだコミットしていない変更の一覧）でも使えます。

ターミナル
git diff --stat src/Api/UserController.cs | 1 + 1 file changed, 1 insertion(+)

この資料に出てくる主なオプション

オプション意味出てくる例
-m "文"メッセージをその場で指定（message）git commit -m "fix"
-a追跡済みファイルの変更を、全部自動でステージしてからコミット（all）git commit -a -m "fix"
-A新規・変更・削除をすべてステージgit add -A
-ustash で、未追跡の新規ファイルも預ける（untracked）git stash push -u
-p変更を1か所ずつ選ぶ（patch）git add -p
-i対話的に編集する（interactive）git rebase -i HEAD~3
--amend直前のコミットを作り直して置き換えるgit commit --amend
--no-editメッセージは変えないgit commit --amend --no-edit
--soft / --hardreset の範囲。soft＝コミットだけ戻す、hard＝作業ツリーまで戻す（何も付けないと mixed）git reset --soft HEAD~1
--stagedステージ側を対象にするgit restore --staged file
--cached手元のファイルは残し、Gitの管理だけ外すgit rm --cached file
--（ハイフン2つだけ）「ここから先はファイル名」という区切りgit commit -m "fix" -- Api.cs
書き換え系の操作は「まだ push していないコミット」だけ

--amend / reset / rebase はコミットのIDを作り変えます。push 済みのコミットに使うと、他の人の履歴とずれます。push 済みの場合は第3章の最後を見てください。

第2章　場面①：作業の途中で、別ブランチの急ぎ作業が入った

状況 feature/login で Login.cs を編集し、Memo.cs（新規メモ）も作った。まだコミットする段階ではない。そこへ「先に別ブランチで Api.cs を直して」と依頼が来た。

2-1　いまの運用（そのまま持ち越し）で何が起きているか

「放置している」ように見えますが、実際には変更が作業ツリーごと一緒に付いてきているだけです。変更はどのブランチのものでもありません。

触っていないファイルなら、切り替えはそのまま成功します。

ターミナル（Api.cs だけ編集している状態）
git switch mainM	Api.csSwitched to branch 'main'

一方、移動先のブランチで同じファイルが違う内容になっていると、Gitが止めてくれます。

ターミナル（Login.cs が main 側でも変更されている場合）
git switch mainerror: Your local changes to the following files would be overwritten by checkout:	Login.csPlease commit your changes or stash them before you switch branches.Aborting
この運用の弱点
  • 「これは別ブランチ用」を頭で覚えておく必要がある
  • git add . や git commit -a を打った瞬間に混ざる
  • 戻ってきたとき、同じファイルを触っていると衝突する

2-2　代わりに何を使うか

やりたいことは「変更をどこかに預けて、ブランチを移って、戻ってきたら受け取る」です。預け先が違う3つの方法があります。

数分〜その日のうちに戻ってくる
→
stash（変更を棚に預ける）
半日〜数日。そのブランチに戻るのを忘れそう
→
WIPコミット（ブランチの履歴に預ける）
何度も行き来する／元の作業に手を触れたくない
→
git worktree（別フォルダで作業する）

2-3　手順A：stash で預ける

stash は、未コミットの変更を一時的にしまっておく棚です。棚は全ブランチ共通で1つなので、メッセージを付けておくと後で迷いません。

  1. 変更を預ける（新規ファイルも一緒に）
    ターミナル
    git stash push -u -m "認証の途中"Saved working directory and index state On feature/login: 認証の途中

    -u は未追跡ファイル（Memo.cs）も預けるオプション、-m はメモです。ブランチ名は Git が自動で記録します。この書き方は「未コミットの変更を全部」預けます。別作業用のファイルだけ預けたい場合は、次の 2-3b を見てください。

  2. 別ブランチで作業してコミットする

    ここは普段どおりです。作業ツリーがきれいなので、何を git add してもよく、混ざる心配がありません。

  3. 元のブランチに戻って、預けた変更を確認する
    ターミナル
    git switch feature/logingit stash liststash@{0}: On feature/login: 認証の途中
  4. 受け取る（棚には残したまま）
    ターミナル
    git stash apply
  5. 元に戻ったことを確認してから、棚を空ける
    ターミナル
    git status -sgit stash drop
stash でつまずきやすい点
  • -u を付け忘れると、新規ファイルは預けられません。実際に git stash push -m "認証の途中" だけで試すと、?? Memo.cs が作業ツリーに残りました。
  • -m なしでも使えますが、メモは WIP on feature/login: f2732e0 init のように「ブランチ名＋直前のコミット名」になり、中身のヒントにはなりません。
  • git stash pop は「受け取る＋棚から削除」を一度にやります。慣れるまでは apply → 確認 → drop の方が安全です。
  • 受け取るときに衝突しても、棚の中身は残っています。
  • drop し間違えたら、直後なら画面に出た Dropped refs/stash@{0} (ハッシュ) のハッシュで git stash apply ハッシュ して戻せます。
  • 特定のファイルだけ預けるなら git stash push -m "メモ" -- Login.cs。

2-3b　stash には何が入る？　ファイルを指定できる？

先に答えると、ファイルを指定して預けられます。何も指定しないと「追跡済みファイルの未コミットの変更を全部」預けます。

状態何も指定しないと入れる方法
追跡済みファイルの、未ステージの変更入る—
ステージ済みの変更入る—
新規の未追跡ファイル入らない-u を付ける
すでにコミットしたもの入らない（stash は「未コミットの変更」だけを預かる）—
.gitignore の対象入らない-a を付ける

ファイルを指定して預ける

状況：Api.cs と Login.cs を編集済み、Memo.cs は新規。このうち別作業用の Login.cs だけを預けます。

ターミナル
git status -s M Api.cs M Login.cs?? Memo.csgit stash push -m "Login.csだけ" -- Login.csSaved working directory and index state On feature/login: Login.csだけgit status -s M Api.cs?? Memo.cs← Api.cs は手元に残ったまま、Login.cs だけが預けられたgit stash show --stat Login.cs | 2 +- 1 file changed, 1 insertion(+), 1 deletion(-)

複数のファイルと新規ファイルを一緒に預けるなら、-u を付けてファイル名を並べます。

ターミナル
git stash push -u -m "Login.csとMemo.cs" -- Login.cs Memo.csSaved working directory and index state On feature/login: Login.csとMemo.csgit status -s M Api.cs
新規ファイルをパス指定するときは -u が必須です
ターミナル（-u を付けなかった場合）
git stash push -m "メモだけ" -- Memo.cserror: pathspec ':(,prefix:0)Memo.cs' did not match any file(s) known to gitDid you forget to 'git add'?

ほかに、git stash push --staged（Git 2.35 以降）はステージ済みの変更だけを預けます（実際に確認済み）。先に預けたいファイルだけ git add して使う方法です。

「全部預けたあとで混乱しない？」を実際に確かめる

心配なのは、全部預けたあと、同じブランチで同じファイルをコミットしてから戻すと、わけが分からなくならないかという点です。まず、stash が何を預かるのかを整理します。

  • stash に入るのは、預けた時点の未コミットの変更だけです。すでにコミットしたファイルを巻き込むことはありません。
  • 戻すときは、「預けたときの変更」を今のファイルに合流させる処理になります。
  • 困るのは、預けている間に、同じファイルの同じ箇所が別の内容に変わった場合です。この場合、Gitは黙って壊さず、衝突として教えてくれます。

実際にやってみます。Login.cs と Api.cs を含めて全部預けたあと、Login.cs を別の内容でコミットし、そのあと戻します。

ターミナル（同じブランチで戻す場合）
git stash push -m "all"# Login.cs と Api.cs の変更が預けられる（Memo.cs は -u なしなので手元に残る）# ここで Login.cs を別の内容に編集して、そのままコミットしてしまったgit commit -a -m "Login.cs を別の内容でコミットしちゃった"git stash applyAuto-merging Login.csCONFLICT (content): Merge conflict in Login.csgit status -sM  Api.csUU Login.cs?? Memo.csgit stash liststash@{0}: On feature/login: all← stash は残っている（失われていない）

結果の読み方です。

  • Api.cs：衝突せずに戻り、ステージ済み（緑のM）になった。
  • Login.cs：UU＝衝突。コミットした内容と預けた内容が食い違っている。
  • stash は消えていないので、やり直しも、あとで戻すこともできます。

なお、別の行の変更どうしなら、自動で合流して衝突しません（実際に、同じファイルの別の行を変更した場合は、両方の変更が入って戻りました）。

別のブランチで戻す場合

同じ仕組みです。戻す先のブランチで、そのファイルが違う内容になっているかどうかで結果が決まります。

戻す先の状態結果（実際に確認）
預けたファイルが、戻す先でも同じ内容そのまま戻る（On branch other / M Login.cs）
預けたファイルが、戻す先で別の内容に変わっている衝突（CONFLICT (content): Merge conflict in Login.cs → UU Login.cs）。stash は残る
預けたファイルに、戻す先で未コミットの変更があるGitが止める（error: Your local changes to the following files would be overwritten by merge → Aborting）。何も変わらない

stash は「どのブランチ用か」を自動では守りません。git stash list に On feature/login: ... と元のブランチ名は出ますが、別のブランチでも戻せてしまいます。意図したブランチで戻すのは自分で確認します。

混乱を避けるコツ

  1. 預けるのは「別作業用のファイルだけ」にする（-- ファイル名 を付ける）。今の作業のファイルが巻き込まれません。
  2. 戻す前に中身を確認する：git stash show -p で差分が見られます。
  3. 長く預けっぱなしにしない。数日以上なら WIPコミットの方が、ブランチに紐づいて迷子になりません。
  4. メモ（-m）には「ブランチ名: 内容」を書いておく。
衝突したときの対処
  1. git status -s で UU のファイルを確認する。
  2. そのファイルを開き、<<<<<<< ・ ======= ・ >>>>>>> で囲まれた部分を、残したい内容に直して、これらの記号を消す。
  3. git add ファイル名 で「解決した」と伝える。
  4. stash は残っているので、不要になったら git stash drop。

適用そのものをやめたい場合：git reset --hard で、戻す前の状態に戻れます。stash は残るので、預けた変更は失われません。ただし reset --hard は未コミットの変更を消す操作です。戻す前に git status を見て、ほかに未コミットの変更がないことを確認してから実行します（stash の適用は、同じファイルに未コミットの変更があると実行されないため、通常は適用の前後でほかの変更は増えていません）。

2-4　手順B：WIPコミットで預ける

変更をそのブランチの履歴に仮のコミットとして置いておく方法です。他のブランチに混ざりようがなく、git log に「WIP」と見えるので、何のための退避か一目で分かります。

  1. 全部まとめて仮コミットする
    ターミナル
    git add -Agit commit -m "WIP: 認証の途中"[feature/login c6ded77] WIP: 認証の途中 2 files changed, 2 insertions(+) create mode 100644 Memo.cs
  2. 別ブランチへ移って作業する

    git switch main など。作業ツリーは空なので、普通にコミットできます。

  3. 戻ってきたら、仮コミットだけ取り消す
    ターミナル
    git switch feature/logingit reset HEAD~1Unstaged changes after reset:M	Login.csgit status -s M Login.cs?? Memo.cs

    コミットだけが消え、ファイルの中身は作業ツリーに残ります。Memo.cs は未追跡に戻ります。

WIPコミットのまま push しないでください

戻し忘れ防止は git log --oneline で「WIP」が見えるかどうか。見えたら未処理です。

2-5　手順C：worktree で別フォルダにする

worktree とは

1つのリポジトリ（.git）を共有したまま、作業ツリー（ファイルを編集するフォルダ）を複数持つ機能です。ブランチごとに別のフォルダを開けるので、ブランチの切り替えそのものが要らなくなります。

clone との違い

別フォルダに git clonegit worktree add
履歴丸ごとコピーして独立共有（コピーしない）
別フォルダでコミットした内容push / fetch しないと届かないすぐ同じリポジトリに入る
ディスク使用量履歴の分だけ増える作業ファイルの分だけ

どういうケースで使うか

場面worktree でどうなるか
作業中に、急ぎの修正（hotfix）が入った別フォルダで hotfix を作業。元のフォルダは何も触らずに済む
他の人のブランチをレビューするために動かしたいレビュー用のフォルダを作って動かし、終わったら削除
長いビルドやテストを走らせながら、別の作業をしたいビルド中のフォルダと、作業用のフォルダを分けられる
2つのブランチの動きを見比べたいエディタやIDEを2つのフォルダで並べて開ける
AIコーディングエージェントなどを、並行して複数走らせたいそれぞれ別フォルダ・別ブランチにすれば、互いのファイルを壊さない

便利なところ（メリット）

  • 切り替えがゼロ。stash も WIPコミットも要りません。
  • 未コミットの変更が混ざりません。フォルダが別なので、別ブランチ用の変更を間違えてコミットする余地がありません。
  • ビルドし直しが減ります。ブランチを切り替えないので、bin / obj のようなビルド成果物が書き換わりません。
  • エディタやIDEを別ウィンドウで並べて開けます。
  • 履歴は共有なので、clone より軽く、コミットもすぐ共有されます。

気をつけるところ（デメリット・制約）

実際に動かして確認した挙動です。

第3章　場面②：うっかり混ざった状態でコミットしてしまった

状況 Api.cs の修正だけをコミットするつもりで git add -A。気づいたら作業途中の Login.cs と、ただのメモ Memo.cs も入っていた。まだ push はしていない。

3-1　まず何が入ったかを確認する

ターミナル

--stat は、ファイルごとの変更行数の表を出すオプションです（git status -s の -s とは別物。詳しくは 1-3）。

ここから「混ざったファイルを外す」のですが、その前に、使う道具 --amend の仕組みを理解しておきます。

3-2　--amend の仕組み

git commit --amend は、直前のコミットを「そのコミットの中身＋今のステージの中身」で作り直して、置き換えるコマンドです。ステージに入っていないものは材料にならないので、「未ステージの変更は混ざらない」ことになります。

1. ファイルの状態を決める

2. 実行するコマンド

3. 結果

    コミットせずに手元へ残るもの

      実際にターミナルで試した出力を見る

      1. 念のため、今の位置に印をつけておく

        git branch backup/before-rebase

      git rebase --abort で rebase を始める前の状態に戻れます。また、後ろのコミットが同じファイルを触っていると、積み直しで衝突することがあります。

      3-9　もう push してしまっていたら

      • 自分1人のブランチなら、書き換えたあとに git push --force-with-lease。他人の変更を上書きしない安全版の強制pushです。
      • 他の人も使っているブランチなら、書き換えずに新しいコミットで直すのが基本です（例：git rm --cached して通常のコミット）。

      第4章　予防：そもそも混ぜない

      4-1　ファイルを名指ししてコミットする

      git commit -m "メッセージ" -- ファイル名 とすると、ステージの状態に関係なく、指定したファイルだけがコミットされます。未コミットの変更を置いたまま作業する運用と相性が良い方法です。

      ターミナル（Login.cs は誤ってステージ済み）
      git status -s M Api.csM  Login.cs?? New.csgit commit -m "fix: apiだけ" -- Api.cs[main 8f15210] fix: apiだけ 1 file changed, 1 insertion(+)git status -sM  Login.cs?? New.cs← Login.cs はステージ済みのまま残り、コミットには入っていない
      新規ファイルは先に git add が必要です
      ターミナル
      git commit -m "new" -- New.cserror: pathspec 'New.cs' did not match any file(s) known to git

      git add New.cs をしてから、もう一度コミットします。

      4-2　同じファイルの中で行単位に選ぶ

      git add -p は、変更を1か所ずつ表示して「入れるか」を聞いてくれます。

      入力意味
      yこの変更をステージに入れる
      n入れない
      sさらに細かく分割する
      q終了する

      ターミナル
      git status -s# 左の列＝コミットされるものgit diff --staged# ステージ済みの中身を最終確認

      git add . や git add -A の代わりに git add ファイル名 と名指しで追加するクセをつけるだけでも、混ざる事故はかなり減ります。

      第5章　やらかしたときの戻し方

      Git は HEAD が動いた履歴を reflog に記録しています。コミットに関する操作は、ほとんどここから戻せます。

      5-1　例：amend で余計なファイルまで混ぜてしまった

      ターミナル
      git reflog -3000234f HEAD@{0}: commit (amend): feat: a42de403 HEAD@{1}: commit (initial): feat: a# HEAD@{1} が amend する前の状態git reset --soft HEAD@{1}git status -sM  b# 混ぜてしまった変更が、ステージ済みで戻ってきたgit restore --staged bgit status -s M b← コミットには入れず、手元の変更として残った

      5-2　状況別の戻し方

      状況戻し方
      git add しすぎたgit restore --staged ファイル名（手元の編集は消えない）
      commit / --amend 直後に戻したいgit reflog で1つ前を探す → git reset --soft HEAD@{1}（変更はステージ済みで残る）
      rebase の途中で迷子になったgit rebase --abort
      rebase が終わったあとに戻したいgit reflog で rebase を始める前の行を探し、そのIDへ git reset --hard ID（または git reset --hard ORIG_HEAD）
      stash drop してしまった直後なら、表示されたハッシュで git stash apply ハッシュ
      ORIG_HEAD について

      ORIG_HEAD は reset や rebase の直前の位置を覚えておく目印ですが、--amend では更新されません。実際に試して確認しました。amend を戻すときは git reflog の HEAD@{1} を使います。

      戻せないもの：コミットしていない変更

      git reset --hard や、作業ツリーを戻す git restore ファイル名（--staged なし）は、まだコミットしていない変更を消します。reflog にも残らないので戻せません。怖い操作の前には、次のどちらかで退避しておきます。

      ターミナル
      git stash push -u -m "退避"# 未コミットの変更を預けるgit branch backup/xxx# 今のコミット位置に印をつける（rebase 前など）

      * を含むパターンは、シングルクォートで囲みます（シェルに展開される前に、Gitへ渡すため）。また、git add した新規ファイルは、コミット前でもこの一覧に出ます（「ステージにあるもの」を表示するため）。

      6-2　管理されているファイルを「探す」

      ファイル名で探す

      ターミナル
      git ls-files '*Login*'src/Api/LoginController.cssrc/Auth/LoginService.cs# ↑ Git自身のパターン指定。フォルダの奥まで探すgit ls-files | grep -i controllersrc/Api/LoginController.cssrc/Api/UserController.cs# ↑ 一覧を grep で絞る（-i は大文字小文字を区別しない）。PowerShell なら下の行git ls-files | Select-String controller

      ファイルの中身で探す

      ターミナル
      git grep -n "Controller"src/Api/LoginController.cs:1:class LoginController { }src/Api/UserController.cs:1:class UserController { }# -n：行番号も表示git grep -l "Login"src/Api/LoginController.cssrc/Auth/LoginService.cs# -l：一致したファイル名だけ表示

      git grep は、管理されているファイルの中だけを検索します（bin や無視されているファイルは対象外なので、速くてノイズが少ないです）。

      6-3　「このファイルは管理されている？」を調べる

      ターミナル
      git ls-files --error-unmatch src/Api/UserController.cssrc/Api/UserController.cs← パスが表示されれば、管理されている（終了コード 0）git ls-files --error-unmatch Memo.cserror: pathspec 'Memo.cs' did not match any file(s) known to gitDid you forget to 'git add'?# ↑ エラーになれば、管理されていない（終了コード 1）

      ファイルが無視されている理由を知りたいときは、git check-ignore -v を使います。どの .gitignore の何行目のルールが効いているかが分かります。

      ターミナル
      git check-ignore -v app.local bin/out.dll.gitignore:2:*.local	app.local.gitignore:1:bin/	bin/out.dll

      6-4　状態で絞る（変更中・未追跡・無視されている）

      ターミナル
      git ls-files -mdocs/README.md# -m：管理中のファイルのうち、変更されているものgit ls-files --others --exclude-standardMemo.cs# 未追跡のファイル（.gitignore で無視されているものは除く）git ls-files --others --ignored --exclude-standardapp.localbin/out.dll# .gitignore で無視されているファイル

      6-5　別のブランチや過去の時点のファイル一覧

      git ls-files は「いま」の一覧です。特定のコミットやブランチ時点の一覧は git ls-tree を使います。

      ターミナル
      git ls-tree -r HEAD --name-only.gitignoredocs/README.mdsrc/Api/LoginController.cssrc/Api/UserController.cssrc/Auth/LoginService.cs# HEAD の代わりに、main や feature/login、コミットIDも指定できる。-r はフォルダの中までgit log --oneline -- 'src/Auth/*'53de124 init# そのパスを変更したコミットの履歴
      ここでも -s には注意

      git ls-files -s は「短く表示」ではなく --stage（ステージの情報を表示）です。実際に出力すると 100644 89931ee… 0 docs/README.md のように、ファイルの種類とハッシュが出ます。詳しくは 1-3。

      第7章　早見表

      やりたいことコマンド
      指定ファイルだけコミットgit commit -m "msg" -- a.cs b.cs（新規は先に git add）
      行単位で選んでコミットgit add -p → git commit
      別作業用のファイルだけ stashgit stash push -u -m "ブランチ名: 内容" -- a.cs b.cs（新規ファイルには -u が必要）
      ステージ済みだけ stashgit stash push --staged -m "メモ"（Git 2.35 以降）
      stash の一覧・中身の確認git stash list ／ git stash show -p
      stash を戻す（安全な順）git stash apply → 確認 → git stash drop
      作業をブランチに紐づけて退避git add -A → git commit -m "WIP" → 戻ったら git reset HEAD~1
      並行作業（別フォルダ）git worktree add ../dir -b 新ブランチ 元 ／ 終わったら git worktree remove ../dir
      直前のコミットに混ぜるgit add ... → git commit --amend --no-edit
      直前のコミットからファイルを外す（手元に残す）git reset HEAD~ -- file → git commit --amend --no-edit
      古いコミットからファイルを外すgit rebase -i で edit → 上の2行 → git rebase --continue
      Git管理から外す（手元に残す）git rm --cached file ＋ .gitignore に追加 → コミット
      直前のメッセージを直すgit commit --amend --only -m "新"
      古いメッセージを直すgit rebase -i で reword
      直近N個を1個にまとめるgit reset --soft HEAD~N → git commit -m "..."
      ステージを取り消すgit restore --staged file
      コミット操作のやらかしを戻すgit reflog → git reset --soft HEAD@{1}
      管理しているファイルの一覧git ls-files（絞り込み：git ls-files '*Login*'）
      管理ファイルの中身を検索git grep -n "文字列"
      このファイルは管理されている？git ls-files --error-unmatch パス
      未追跡・無視されているファイルの一覧git ls-files --others --exclude-standard ／ git ls-files --others --ignored --exclude-standard
      変更ファイルと行数の一覧git diff --stat ／ git show --stat

      おすすめの運用

      1. 短い寄り道は git stash push -u -m "ブランチ名: 内容" -- 別作業のファイル（ファイルを指定して預ける）。
      2. 半日以上の別作業は WIPコミット。
      3. 並行作業が日常なら git worktree。
      4. コミットするときは git commit -m "..." -- ファイル名 で名指しする。
      5. 混ざったら git reset HEAD~ -- file → git commit --amend --no-edit。
      6. rebase など怖い操作の前は git branch backup/xxx で印をつける。

      用語

      用語意味
      HEAD今いるブランチの最新コミットを指す目印
      HEAD~HEAD の1つ前のコミット（HEAD~3 は3つ前）
      追跡済み／未追跡Gitが管理している／まだ管理していないファイル
      ステージ／インデックス次のコミットに入れる予定の変更を置く場所
      reflogHEAD が動いた履歴。コミット操作の取り消しに使う
      WIPWork In Progress。作業途中の意味
      amend直前のコミットを作り直して置き換えること
      worktree同じリポジトリを共有した、別フォルダの作業ツリー
      --「ここから先はファイル名」という区切り
